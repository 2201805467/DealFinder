# قاعدة بيانات المنتجات والعروض — المرحلة الثالثة

تحديث المرحلة السابعة: أصبح هناك مصدران عامان ببيانات فعلية، وعلاقة المصدر بالبائع و metadata للمنصة والانتهاء والإسناد، معموقعبائع اختياري. `view=all` يتيحالعروضالمجانيةالصحيحة؛يبقى discounted افتراضيًا للتوافق. [السياسات والحالة الحالية](DATA_SOURCES.md). الفقرات التالية توثق أساس المرحلة الثالثة وبياناتها الاصطناعية التاريخية.

بيانات التطوير الحالية اصطناعية بالكامل. بدء المرحلة الثالثة تم بطلب صاحب المشروع رغم بقاء تصريح المصدر التجاري غير متاح؛ لا يُعد هذا إغلاقًا لتكامل تجاري في المرحلة الثانية. BestBuyProvider وWooCommerceProvider وعقد StoreProvider محفوظة دون تغيير.

## التشغيل والترحيل

من `backend` بعد ضبط `.env` وتشغيل PostgreSQL:

```powershell
npm.cmd ci
npm.cmd run prisma:generate
npm.cmd run db:migrate
npm.cmd run db:seed
npm.cmd run dev
```

`db:migrate` يستخدم Prisma migrate deploy لتطبيق الترحيلات المراجعة؛ لا ينفذ reset أو db push ولا يحذف بيانات التطوير. Migration الحالية `202611170001_catalog` تنشئ الجداول والفهارس وقيود CHECK والمفاتيح الأجنبية. لإضافة تعديلات مستقبلية أنشئ Migration جديدة؛ لا تعدل SQL لترحيل طُبق بالفعل. [مرجع Prisma Migrate](https://www.prisma.io/docs/orm/v7/prisma-migrate/getting-started).

Seed اختياري للتطوير، ومحصور ببيئة development أو test وعنوان Loopback وقاعدة محلية معروفة. يضيف متجرين DEMO وثلاثة تصنيفات و12 منتجًا/عرضًا اصطناعيًا، منها عرض منتهٍ ومنتج بلا سعر. يتكرر دون حذف سجلات قائمة أو دمج الأسماء المتشابهة. لا يتصل بمتجر خارجي ولا ينسخ صورًا؛ روابط `.example.invalid` توضيحية فقط. في الإنتاج تمنع خدمة الإدخال البيانات الاصطناعية وتستبعدها استعلامات الخادم.

## الجداول والعلاقات

| الجدول | العلاقات والهوية |
| --- | --- |
| `merchants` | اسم ونوع مصدر وموقع فريد وتفعيل، وموافقة تخزين ومرجعها وسياسة الاحتفاظ؛ يرتبط بعروض وسجلات إدخال ومصدر محتوى المنتج |
| `categories` | شجرة عبر parent_id؛ حذف الأب الذي له أبناء ممنوع، وحذف تصنيف منتج يزيل ارتباط التصنيف فقط |
| `products` | الاسم والوصف والصورة والتصنيف والطوابع الزمنية، مع مصدر المحتوى وانتهائه ووسم البيانات الاصطناعية؛ له عدة عروض |
| `offers` | هوية المصدر والأسعار والعملة والسوق والمتغير والروابط والتوفر وتاريخ الجلب والانتهاء؛ يرتبط بمنتج ومتجر |
| `sync_runs` | متجر/مصدر وحالة وعدد معالج وبداية ونهاية وكود خطأ وتفاصيل آمنة لكل دفعة إدخال؛ ليس مشغل مزامنة |

هوية العرض الفريدة: `(merchant_id, external_product_id, market, variant_key, currency)`. المعرف الخارجي لا يكون فريدًا عالميًا. القيم المفقودة للسوق/المتغير/العملة تمثل داخليًا بسلسلة فارغة لتجنب ثغرة NULL في Unique، وتعود `null` في API. لا يُسمح بسعر دون عملة صريحة. اختلاف المتجر أو السوق أو المتغير أو العملة ينشئ هوية عرض مستقلة.

لكل عرض Product منفصل افتراضيًا. ربط عرض من متجر آخر بمنتج موجود يحتاج `productId` صريحًا ومتحققًا منه عند الإدخال؛ الاسم المتشابه لا يربط المنتجات. يحتفظ المنتج بمصدر نصه وصورته حتى لا تعيد عروض أخرى نشر محتوى انتهت صلاحيته أو سحبت موافقة مصدره.

الأسعار `Decimal(24,6)` والنسبة `Decimal(7,4)`، ويُجرى الحساب بـPrisma Decimal، مع تقريب النسبة إلى منزلتين. API تعيد الأسعار والنسب كنصوص عشرية، لا أرقام JSON عائمة. عدد المنازل في النص قد يختلف دون تغيير القيمة. القيمة الصفرية صالحة، والمرجع يجب ألا يقل عن السعر الحالي. لا يوجد سجل تاريخ أسعار.

## خدمة إدخال StoreProvider

`OfferIngestionService.ingest(merchantId, items)` داخل `src/services/offer-ingestion.ts` تقبل بيانات StoreProduct مع سياق اختياري: `variantKey` و`affiliateUrl` و`categoryId` و`productId`. لا توجد واجهة كتابة عامة أو تشغيل تلقائي لمزود في هذه المرحلة.

- يتحقق اسم المصدر والبيانات والروابط والتوقيت والعملات. أرقام StoreProvider الحالية تحول إلى نص ثم Decimal دون حساب مالي عائم. لا يمكن استرجاع الدقة التي فُقدت في مزود قبل الوصول للخدمة؛ لذلك ترفض الأرقام غير الآمنة وآثار float الظاهرة وأكثر من ست منازل بدل تقريبها صامتًا. لم يُغير عقد المزودات.
- تُحسب النسبة من السعرين القابلين للمقارنة؛ لا تُعتمد النسبة الواردة من المزود ولا تعتبر إثباتًا لجودة الصفقة. `priceRestricted` يحجب تخزين السعرين والنسبة.
- التحقق من سياسة المتجر وقفلها أثناء الدفعة، مع قفل PostgreSQL للهوية قبل Upsert لمنع إنشاء منتجات مكررة عند التزامن. تراجع الدفعة كاملة عند خطأ؛ لا تبقى منتجات يتيمة من محاولات فاشلة. [معاملات Prisma](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).
- لا يستبدل جلب أقدم بيانات أحدث. ينشأ SyncRun للدفعة المصرح بمحاولة إدخالها، وينتهي بنجاح أو فشل آمن دون استجابة المصدر أو أسراره. مدخلات غير صالحة قبل بدء الدفعة أو سياسة غير مصرح بها ترفض قبل إنشاء سجل تشغيل.

## سياسات الاحتفاظ

المتجر غير مفعل وغير مصرح بالتخزين افتراضيًا. قبل أي بيانات حقيقية يلزم تصريح موثق في `authorizationReference` وضبط `storageAuthorized` ومدة `retentionSeconds`. لا يسمح بغياب المدة إلا عند إقرار `allowIndefiniteRetention` صراحة بعد مراجعة الترخيص؛ ليس ذلك الإعداد الافتراضي. موافقة المصدر الخارجية لا يكتشفها النظام تلقائيًا، وإدخال قيمة في الحقل لا ينشئ ترخيصًا قانونيًا.

يحسب expiresAt من وقت جلب المعلومات الأصلي، وليس وقت حفظها، للمنتج ومعلومات العرض. تستبعد القراءة تاريخ الانتهاء المساوي للحظة الحالية أو الأقدم، وعروض المتاجر المعطلة أو المسحوبة موافقتها، ومحتوى المنتج الذي انتهت صلاحيته ولو وجد عرض آخر مرتبط به.

انتهاء صلاحية العرض لا يمحو تلقائيًا منتجًا ما زال له محتوى مصرح صالح. للتخلص الفعلي من المحتوى المنتهي يوجد أمر صريح، دون جدولة:

```powershell
npm.cmd run db:purge-expired
```

يحذف العروض المنتهية، ويمحو النص والصورة المنتهيين من المنتجات ويزيل السجلات المنتهية اليتيمة. لا يحذف عرض متجر آخر صالحًا لمجرد انتهاء محتوى المنتج؛ قد يبقى ارتباطه مخفيًا حتى تحديث بيانات المنتج من مصدر مصرح. لا توجد Jobs، لذا يجب على المشغل تنفيذ الإزالة قبل تجاوز مدة الترخيص الفعلية. إخفاء API وحده ليس بديلًا للحذف من القرص. أي تغيير في سياسة المصدر يحتاج مراجعة بياناته الموجودة وإزالة ما لم يعد مصرحًا به؛ لا توجد واجهة إدارة سياسة تلقائية هنا.

## REST API

المسارات:

- `GET /api/v1/deals` و`GET /api/v1/deals/:id`
- `GET /api/v1/products` و`GET /api/v1/products/:id`
- `GET /api/v1/categories` و`GET /api/v1/merchants`

Deals تعني عروضًا ذات نسبة محسوبة موجبة وغير مصنفة UNAVAILABLE، وليست درجة جودة. التوفر UNKNOWN يبقى مجهولًا ولا يثبت المخزون أو الشحن. Products تعرض المنتجات ذات عرض مرئي واحد على الأقل حتى إن كان بلا سعر.

المعرفات UUID. قوائم المنتجات والعروض تدعم:

| المعامل | المعنى |
| --- | --- |
| `page`, `pageSize` | افتراضيًا 1 و20؛ حد الصفحة 100000 والحجم 100 |
| `q` | جزء حرفي من اسم المنتج، دون حساسية لحالة الأحرف؛ `%` و`_` ليسا Wildcards |
| `categoryId` | التصنيف المحدد فقط، دون توسيع تلقائي للأبناء |
| `merchantId` | متجر محدد |
| `market`, `currency` | دولتان حرفيتان أو رمز عملة من ثلاثة أحرف كبيرة |
| `minPrice`, `maxPrice` | نص عشري غير سالب حتى ست منازل؛ يتطلبان currency |
| `sort` | `newest` افتراضيًا، أو `price_asc`, `price_desc`, `discount_desc` |

ترتيب السعر يتطلب currency؛ لا تجري مقارنة أسعار العملات المختلفة ولا تحويلها. بقية الترتيبات قد تعرض عملات متعددة دون ترتيب أسعارها. أسعار المنتجات ترتب بأقل سعر بين العروض المطابقة للمرشحات ضمن العملة نفسها، والخصم بأعلى نسبة مطابقة، والحداثة بأحدث جلب مطابق. التجميع وإزالة التكرار في PostgreSQL قبل Pagination؛ لا تحذف تكرارات بعد تقطيع صفحات العروض.

المخرجات داخل `data`، ومع القوائم `pagination: {page,pageSize,total,totalPages}`. الفراغ يعيد `200` وقائمة فارغة. بيانات المنتجات والعروض تحتوي `isSynthetic` صريحًا؛ الأسماء الاصطناعية تبدأ DEMO. التفاصيل تعرض العروض الصالحة فقط، ولا يُكشف مرجع وثيقة الموافقة. قوائم التصنيفات والمتاجر مخصصة أساسًا لـPagination؛ استخدم مرشحات المنتج في قوائم products/deals.

تحديث المرحلة السادسة: `products` وتفاصيل المنتج تعرض حتى20 عرضًا متداخلًا لكل منتج لمنع تضخم الاستجابة، مع `offersTruncated=true` إن تجاوزت العروض المطابقة السقف. استخدم قائمة deals المرقمة أو `GET /api/v1/products/:id?offerId=<uuid>` للوصول إلى عرض معين، بما فيه fallback للمفضلة ذات السعر المنخفض. لا يتجاوز ذلك قواعد صلاحية العرض. أضيف فهرس `(currency,last_updated_at DESC,id)` وGIN على `lower(name)` بعد القياس في100k؛ راجع [تقرير الأداء](PERFORMANCE_REPORT.md). أخطاء انشغالDB المعروفة تعيد503/Retry-After بدل كشف تفاصيلها.

تحديث6.1: يتوفر Cursor اختياري للأحدث فقط، دون تغيير العقد الذي يستخدمه Flutter:

```text
GET /api/v1/deals?pagination=cursor&sort=newest&currency=USD&pageSize=20
GET /api/v1/deals?pagination=cursor&sort=newest&currency=USD&pageSize=20&cursor=<nextCursor>
```

في هذا النمط فقط يصبح total وtotalPages بقيمة null، ويضاف hasMore وnextCursor. لا يُحسب العدد ولا يُستخدم OFFSET. يتطلب المرشحات وحجم الصفحة نفسيهما وpage=1، وصلاحية الرمز15 دقيقة. ترتيب newest مستقر عبر lastUpdatedAt DESC ثمUUID ASC؛ لا يجمّد تغيرات الكتالوج أو صلاحية العروض، ويُفحص الانتهاء والقدم والموافقة في كل طلب. Cursor غير مدعوم لترتيب Score المتغير زمنيًا أو مسارات products/categories/merchants؛ يعاد400 عند استخدامه هناك. الطلبات الافتراضية باقية كما هي. التفاصيل والقياسات في [PERFORMANCE_OPTIMIZATION.md](PERFORMANCE_OPTIMIZATION.md).

```text
GET /api/v1/deals?currency=USD&sort=price_asc&pageSize=5
GET /api/v1/products?q=DEMO&market=DE&currency=EUR&minPrice=5&maxPrice=100
GET /api/v1/products?categoryId=<uuid>&merchantId=<uuid>&sort=discount_desc
```

أمثلة HTTP التقطت فعليًا من النسخة المبنية وقاعدة التطوير الاصطناعية، بما فيها المسارات الستة وفحص الصحة وطلب خطأ: [API_EXAMPLES.json](API_EXAMPLES.json). المعرفات والطوابع الزمنية تخص هذا التشغيل وليست ثوابت عامة.

الأخطاء `400` للمدخلات أو مقارنة سعر بلا عملة، و`404` للمعرف غير الموجود أو المحتوى المخفي/المنتهي، و`500` للأخطاء غير المتوقعة مع رسالة آمنة. المعرّف ذو الصيغة غير الصالحة يعيد `400`.

## الاختبارات وقاعدة البيانات المنفصلة

```powershell
npm.cmd test
npm.cmd run typecheck
npm.cmd run build
npm.cmd run format:check
```

لا تحتاج هذه الأوامر إلى قاعدة اختبار. اختبارات التكامل تستخدم PostgreSQL مستقلًا؛ من backend أنشئ قاعدة باسم `dealfinder_test` باستخدام حساب PostgreSQL المحلي (الاسم الافتراضي للمستخدم هو dealfinder، عدله إذا غيرته):

```powershell
docker compose exec postgres createdb -U dealfinder dealfinder_test
Copy-Item .env.test.example .env.test
```

تجاوز createdb إذا كانت القاعدة موجودة، ولا تنسخ المثال فوق `.env.test` موجود. ضع بيانات الاعتماد المحلية الصحيحة في TEST_DATABASE_URL داخل `.env.test` المستبعد من Git، دون تعديل DATABASE_URL للتطوير. ثم:

```powershell
npm.cmd run test:integration
```

الحارس يرفض قاعدة التطوير والعناوين البعيدة ويشترط اسمًا ينتهي `_test`. يشغل migrate deploy على الاختبار دون reset أو truncate، ويزيل فقط سجلات تخص الجولة الحالية؛ يحتفظ Seed الاصطناعي القابل لإعادة الاستخدام. اختبارات الإنتاج تتحقق من إخفاء البيانات الاصطناعية، ولا تتصل بمتجر حقيقي.

النطاق أعلاه يوثق المرحلة الثالثة. أضيفت في المرحلة الرابعة مزامنة اصطناعية مجدولة وتقييم؛ راجع [دليل المزامنة](SYNCHRONIZATION.md) لتحديثات Score وstale والثقة واختيارات Deals. لا توجد مصادقة أو مفضلة أو Flutter أو مزامنة تجارية. البحث الجزئي مناسب للحجم الحالي؛ قبل كتالوج كبير يجب قياس خططه وتطوير فهرسة البحث وفق الحاجة، دون افتراض اختبارات أداء لم تنفذ.
