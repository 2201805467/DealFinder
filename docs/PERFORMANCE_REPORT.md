# تقرير الأداء — المرحلة السادسة

تاريخ القياس: 2026-11-18. جميع المنتجات اصطناعية، وجميع طلبات الحمل إلى 127.0.0.1. لا توجد طلبات حمل على متجر خارجي.

## البيئة والمنهج

Windows، Node v24.12.0، PostgreSQL 17 داخل Docker، 16 معالجًا منطقيًا و15.72 GiB RAM. العميل والخادم وقاعدة البيانات على الجهاز نفسه؛ ليست هذه مواصفات خادم إنتاج أو ضمان سعة. الأداة المجانية [autocannon](https://github.com/mcollina/autocannon)، اتصال واحد لكل مستخدم افتراضي، pipelining=1، مهلة اتصال 10s.

قاعدة منفصلة اسمها dealfinder_qa_test، تتضمن 5 متاجر و10 تصنيفات و1,000 / 10,000 / 50,000 / 100,000 منتج وعرض، عملة USD وسوق US. إنشاء/تفريغ Fixtures مقصور بحارس على هذه القاعدة؛ لم تُفرغ dealfinder أو dealfinder_test. لا صور خارجية.

لكل حجم: 8 سيناريوهات فردية، 10 اتصالات لمدة نحو ثانيتين، ثم مزيج المسارات الثمانية لمدة نحو 5 ثوان لكل مستوى. التسلسل المخطط 10،50،100،250،500،1000؛ يتوقف التصعيد إذا تجاوزت الأخطاء 2% أو p95 ثانيتين أو هبط RAM الحر تحت 1GiB. الاختبارات قصيرة استكشافية وليست soak test؛ آخر الطلبات قد تتداخل مع تصفية الطابور. إعداد API_RATE_LIMIT_MAX=1000000 خاص بعملية الحمل المحلية حتى لا نقيس حد 300/min؛ حد التزامن 64 يبقى فعالًا.

العينة النهائية: 2026-11-18T19:58:22.181Z إلى 2026-11-18T20:01:36.394Z UTC، 42 حالة. قبل التحسين: 2026-11-18T19:30:33.443Z إلى 2026-11-18T19:33:36.497Z. ملفات JSON تحفظ التوقيت والطلبات والأخطاء والخطط كاملة.

## نتائج الحمل النهائية الكاملة

## حدود التصعيد والكتالوج الكبير

- 1000 منتج: توقف التصعيد عند 100 اتصال بسبب Latency/error/resource guardrail؛ لم تُختبر المستويات الأعلى لهذه العينة.
- 10000 منتج: توقف التصعيد عند 100 اتصال بسبب Latency/error/resource guardrail؛ لم تُختبر المستويات الأعلى لهذه العينة.
- 50000 منتج: توقف التصعيد عند 50 اتصال بسبب Latency/error/resource guardrail؛ لم تُختبر المستويات الأعلى لهذه العينة.
- 100000 منتج: توقف التصعيد عند 50 اتصال بسبب Latency/error/resource guardrail؛ لم تُختبر المستويات الأعلى لهذه العينة.

عند 1k و10k، تجاوز التزامن 64 يسبب رفضًا مبكرًا 503؛ آلاف ردود الرفض في الثانية ليست سعة أعمال. عند 50k/100k ظهرت مهلات/503 تحت 50 اتصالًا، فتوقف الاختبار. لم يُشغّل 500 أو1000؛ هذه حدود مؤكدة تمنع الادعاء بجاهزية حمل مرتفع. جُرب 250 في خط الأساس عند 1k ثم توقف عند p95=2078ms وأخطاء3.51%.

يظل Score الديناميكي O(n) مع فرز المرشحين، و100k Top Deals عند 10 اتصالات أعطى p95 نحو882ms رغم إزالة فشل الذاكرة. الحل المستقبلي المقترح: تضييق المرشحين بفهارس الشروط، وتخزين المكونات الثابتة فقط مع حساب الحداثة من timestamp وقت الاستعلام؛ أو cache محدود زمنيًا يحمل scoredAt وعتبة صلاحية صريحة. يلزم قياس جديد واختبار ترتيب يعبر حدود الزمن قبل أي تنفيذ. لم يُنفذ cache أو scoring snapshot أو Worker جديد.

OFFSET يظل يتزايد عمله مع العمق؛ العينة لا تثبت كلفة ثابتة، ويتداخل أثر cache/العد. Keyset pagination توصية مستقبلية إذا لزم التوسع؛ لم يتغير عقد ترقيم الصفحات. تُجلب علاقات الصفحة كدفعة عبر Prisma، ولا يوجد استعلام يدوي لكل منتج في loop القراءة. العروض المتداخلة مقيدة بـ20 لكل منتج مع offersTruncated؛ اختيار offerId في تفاصيل المنتج يحافظ على الوصول للعرض المحفوظ خارج أول20. Pool=10، SQL timeout=5s، connection timeout=5s، idle=30s، والقبول64 يقلل نمو الطوابير. Upsert يعيد استخدام الهوية والأقفال والمعاملة الحالية؛ لا يعيد كتابة المنتج إلى مصدر ثانٍ بالاسم.

## Flutter

اختبار اختياري tool/qa_live_ui_test.dart يتصل بـAPI فعلي على loopback لكتالوج100k، يجلب200 عرض فريد في10صفحات، يمرر ويفحص التفاصيل والمفضلة وتغيير الوضع. القياسات في mobile/docs/qa-live-ui.json: فتح Home=3806ms، عشرة scroll/pump=3978ms، كامل الاختبار=17239ms، RSS195510272→335486976 بايت، Widgets بطاقات مركبة4→8 رغم200 نتيجة، ما يثبت البناء الكسول في هذا السيناريو. تتضمن RSS المحرك وإطار الاختبار؛ ليست heap للتطبيق أو دليل تسرب ذاكرة. زمن pumps ليس FPS أوjank علىAndroid. القائمة المقيمة مقيدة1000 مع توجيه لتضييق البحث؛ تؤكدها50صفحة Mock.

تعذر إقلاع Pixel_5: Android Emulator35.4.9 رفض فحص hasSufficientDiskSpace. لا يوجد جهاز ADB متصل؛ لم تُحذف تطبيقات أو بيانات AVD. لم تُجمع DevTools/profile traces أو FPS/ذاكرة هاتف أو سرعة صور حقيقية؛ البيانات الاصطناعية بلا صور خارجية. [Flutter profile mode غير متاح للمحاكي](https://docs.flutter.dev/testing/build-modes)، ويوصى [بقياس الأداء على جهاز فعلي](https://docs.flutter.dev/perf/ui-performance).

## إعادة التجربة والأدلة

من backend بعد npm ci وdb:migrate وbuild:

```powershell
node qa/performance.mjs --label=rerun
node qa/parallelism.mjs
node qa/final-checks.mjs
```

الأمر الأول يعيد إنشاء Fixtures في dealfinder_qa_test فقط ويستهلك موارد محلية؛ لا تشغله ضمن خدمة الإنتاج. parallelism يعيد إظهار الفشل السابق عمدًا على QA فقط. qa/report-performance.mjs يولد هذا التقرير من أدلة baseline/final/EXPLAIN، ولا يعيد الحمل. performance-after.json وperformance-after-large.json محاولتان وسيطتان محفوظتان للتدقيق؛ إحداهما توقفت عند bulk setup timeout قبل إصلاح مهلة إعداد البيانات. ليستا النتائج النهائية.
