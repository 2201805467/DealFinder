# مزامنة المنتجات وتقييم العروض — المرحلة الرابعة

تحديث المرحلة السابعة: أعيد استخدام العامل والخدمات نفسها لمصدري CheapShark و GamerPower الحقيقيين ضمنوضع`--real` مستقل وآمن، مع احتسابالطلباتالفعلية وسياسات Checkpoint المناسبة. لا تبدأمزامنةمع Express،ولا توجدجدولةزحف لـCheapShark. [أوامر التفعيل والسياسات](DATA_SOURCES.md). قسم Demo التالي باقٍللتطوير فقط، وهو ممنوعفي الإنتاج.

المصدر المشغل حاليًا `MockStoreProvider` اصطناعي فقط، دون HTTP خارجي أو صور من متاجر حقيقية. لا يتصل Worker بـBest Buy أو WooCommerce رغم حفظ كودهما. تشغيله التجريبي ممنوع في الإنتاج، ولا يعني نجاحه اعتماد مصدر تجاري.

## التشغيل اليدوي

من `backend` بعد تجهيز PostgreSQL وملف `.env` المحلي:

```powershell
npm.cmd run db:migrate
npm.cmd run worker:seed-demo
$env:WORKER_ENABLED='true'
$env:WORKER_ALLOW_SYNTHETIC='true'
$env:WORKER_PAGE_SIZE='2'
npm.cmd run worker:once
```

يجب أن تكون `NODE_ENV=development` أو `test`. لا تغيّر DATABASE_URL للتطوير إلى قاعدة الاختبار. `worker:seed-demo` يضيف/يفعّل متجرًا اصطناعيًا واحدًا باسم `SYNTHETIC Worker DEMO Store` وعنوان `.example.invalid`، ولا يجلب بيانات. أمر `worker:once` يتجاوز due time مرة واحدة للمصادر المفعلة، مع احترام القفل والحدود والموافقة. الطلبات المعدودة في هذا المثال استدعاءات للمزود الاصطناعي وليست طلبات شبكة تجارية.

المثال يحوي خمسة منتجات، أربعة منها لها أسعار مرجعية اصطناعية أعلى. تكرار الأمر يحدث السجلات نفسها ولا يضاعفها. تحذف عملية التنظيف بيانات انتهت مدتها فقط وفق السياسة، ولا تحذف منتجات لمجرد عدم ورودها في صفحة أو فشل المصدر.

لتشغيل JavaScript المبني بدل tsx:

```powershell
npm.cmd run build
node dist/scripts/worker.js --once
```

للعودة للإغلاق الافتراضي في نافذة PowerShell الحالية:

```powershell
Remove-Item Env:WORKER_ENABLED -ErrorAction SilentlyContinue
Remove-Item Env:WORKER_ALLOW_SYNTHETIC -ErrorAction SilentlyContinue
Remove-Item Env:WORKER_PAGE_SIZE -ErrorAction SilentlyContinue
```

لم تُفعّل هذه الأعلام بشكل دائم في `.env` أثناء التنفيذ. المثال `.env.example` يبقيها false. عنوان المتجر التجريبي ليس وجهة شبكة؛ MockStoreProvider ينشئ بياناته محليًا.

## الجدولة والإيقاف

بعد opt-in السابق:

```powershell
npm.cmd run worker
```

العامل عملية مستقلة عن Express. يستطلع المصادر المفعلة بحسب `WORKER_POLL_MS`، ويستخدم لكل متجر `syncIntervalSeconds` و`nextSyncAt` من PostgreSQL. إعادة فحص موعد المصدر تتم تحت القفل لمنع مطالبة عمليتين بالموعد نفسه. جدولته تعتمد على الزمن في قاعدة البيانات وتستمر مواعيدها عند إعادة تشغيل العامل؛ لا تعتمد على cron أو Redis.

يضبط المثال المصدر بفاصل 300 ثانية وعتبة قدم 900 ثانية. لتعديل المصدر التجريبي فقط، يمكن تنفيذ SQL إداري محلي، أو تعديل السجل بأداة إدارة PostgreSQL:

```sql
UPDATE merchants
SET sync_interval_seconds = 300,
    stale_after_seconds = 900,
    next_sync_at = NULL
WHERE website_url = 'https://worker.example.invalid'
  AND is_synthetic = true;
```

`syncEnabled` مستقل عن تفعيل المتجر وموافقة التخزين. عند إيقافه لا تبدأ مزامنة جديدة، ويتحقق الإدخال مجددًا من السياسة أثناء كل صفحة. تصفير nextSyncAt مفيد عند تغيير الموعد لتطبيقه في أقرب tick. مدة القدم الجديدة تطبق على جلب جديد؛ لا تغير الطوابع الموجودة بأثر رجعي.

يدعم المدخل SIGINT/SIGTERM: يتوقف اختيار مصادر جديدة، ويلغي الطلب/Backoff الحاليين، وينتظر التراجع أو حفظ الصفحة الجارية وإغلاق اتصالات DB. الصفحات التي حُفظت قبل الإيقاف تبقى محفوظة. اختبارات AbortSignal أثبتت تحرير القفل وإمكانية تشغيل لاحق؛ لا يُفترض أن إنهاء عملية بالقوة على كل أنظمة التشغيل يمر بمعالج الإشارة. عند خروج قسري، يحرر PostgreSQL القفل بانتهاء الاتصال، وتُسجل RUNNING القديمة كـWORKER_INTERRUPTED عند المطالبة التالية.

## الإعدادات والحدود

| الإعداد | الافتراضي | الغرض |
| --- | --- | --- |
| `WORKER_ENABLED` | false | إذن تشغيل صريح |
| `WORKER_ALLOW_SYNTHETIC` | false | إذن بيانات الاختبار؛ لا يسمح بالإنتاج |
| `WORKER_POLL_MS` | 5000 | فترة استطلاع مواعيد المصادر |
| `WORKER_CLEANUP_MS` | 60000 | فترة حلقة تنظيف مستقلة عن بطء جلب المصادر |
| `WORKER_REQUEST_TIMEOUT_MS` | 10000 | مهلة محاولة طلب المزود |
| `WORKER_MAX_RUN_MS` | 60000 | مهلة عمل المزامنة؛ يليها إغلاق المعاملات وتسجيل النتيجة |
| `WORKER_MAX_PAGES` | 10 | أقصى صفحات ناجحة لكل تشغيل |
| `WORKER_MAX_PRODUCTS` | 200 | أقصى سجلات تعالج لكل تشغيل |
| `WORKER_MAX_REQUESTS` | 20 | أقصى محاولات المزود، بما فيها Retry |
| `WORKER_PAGE_SIZE` | 20 | حجم صفحة ثابت أثناء offset pagination |
| `WORKER_MAX_RETRIES` | 3 | عدد الإعادات بعد المحاولة الأولى |
| `WORKER_BACKOFF_MS` | 500 | قاعدة Backoff |
| `WORKER_MAX_BACKOFF_MS` | 30000 | سقف نمو Backoff؛ لا يقصر Retry-After |

عدد المنتجات المعالجة ليس عدد معرفات فريدة؛ قد يرد المعرف مرتين من المصدر ويظل Upsert يمنع تكرار سجله. إذا تجاوزت صفحة أخيرة الميزانية، يحفظ الجزء المسموح ويسجل PRODUCT_LIMIT، دون تغيير pageSize في وسط ترقيم offset. تتوقف Cursor متكررة بإشارة واضحة. الطلب الفارغ لا يأمر بحذف البيانات.

Network/Timeout/Rate Limit/Upstream يمكن إعادة محاولتها ضمن الحدود. التأخير الأساسي `min(maxBackoff, base * 2^attempt)`، مع Equal Jitter عشوائي بين نصفه وكامله، ثم يؤخذ الأكبر بينه وبين Retry-After. لا تُعاد أخطاء الوصول/الحصة المبهمة تلقائيًا. إذا تجاوز Retry-After الزمن المتبقي تنتهي الجولة بدل إرسال طلب مبكر أو انتظار غير محدود. المحاولات تشمل الطلب الفاشل ولا تعيد إدخال صفحة حُفظت بالفعل. كل استدعاء بحث للمزودات الحالية يرسل طلبًا واحدًا على الأكثر؛ أي مزود مستقبلي يجمع عدة طلبات داخليًا يحتاج دمج حسابها مع الميزانية قبل تفعيله.

تحديث المرحلة السادسة: عند تجاوز الحدود تكون النتيجة PARTIAL، ويحفظ `merchants.syncCheckpoint` الصفحة/cursor وpageSize وoffset داخل الصفحة وبصمة المصدر/إصدار pagination ووقت الحفظ وعلامة نقص التغطية. يُحفظ Checkpoint في معاملة إدخال الصفحة نفسها، وتستأنف الجولة التالية البقية بدل البدء من أول صفحة. عند تغيير ميزانية المنتجات يبقى حجم الصفحة السابق ثابتًا؛ يحفظ الجزء الباقي دون تخطيه. صلاحية Checkpoint يوم واحد، وتغير المصدر/الإصدار يبدأ مسحًا جديدًا. انتهاء دورة ناجحة يمحو Checkpoint.

إذا أعلن المزود `stablePagination=true` يجوز اعتبار دورة موزعة على جولات كاملة بعد آخر صفحة سليمة. دون هذا الضمان تبقى نتيجة الاستكمال PARTIAL/UNSTABLE_PAGINATION حتى لو وصلت لآخر صفحة؛ تغير الكتالوج بين الطلبات لا يثبت snapshot شاملًا. صفحات partial/skipped تبقي INCOMPLETE_CYCLE عند الاستكمال؛ لا تُحذف المنتجات الغائبة. Mock الحالي يضمن الثبات، والمزودان التجاريان لا يعلنان هذا الضمان. اختبرت المرحلة السادسة2000 عنصر عبر جولات محدودة وإعادة تشغيل عملية حقيقية، دون جوع الصفحات الأخيرة.

الجولة المحدودة ذات Checkpoint تسجل موعد استكمال بعد `WORKER_POLL_MS` بدل انتظار دورة التحديث الكاملة، مع احترام `syncNotBefore` إذا وجد Retry-After. تُحفظ هذه المهلة في PostgreSQL وتطبق حتى على manual force وإنشاء Worker جديد؛ `worker:once` يتجاوز due time العادي فقط.

## القفل والمعاملات والتسجيل

يستخدم المصدر `pg_try_advisory_xact_lock` بمفتاح مشتق من UUID المتجر ونطاق خاص بالعامل. يحصل مصدر مشغول على SOURCE_BUSY فورًا. جُرب المنع من عميلَي DB منفصلين ومن عملية Node أخرى. المعاملة الحاملة للقفل محدودة بعمر الجولة مع مهلة لإغلاق عمليات DB؛ لا تحتوي كتابات المنتجات، فهي تحفظ صفحة صفحة بمعاملات خدمة الإدخال الحالية حتى لا يمحو خطأ صفحة لاحقة العمل الناجح.

هذا الأسلوب يحتجز اتصال PostgreSQL أثناء الجولة، وهو مناسب للحجم الحالي المحدود. يجب توفير سعة اتصالات للعمل والتخزين والتنظيف، واستخدام PostgreSQL مباشر يدعم الأقفال؛ لم تُختبر إعدادات Proxy أو PgBouncer. في المرحلة السادسة اختُبر إنهاء اتصال coordinator فعليًا أثناء الجلب؛ لا تُكتب النتيجة المتأخرة، وتستعيد جولة لاحقة العمل. `syncGeneration` يزداد عند المطالبة ويُفحص تحت قفل صف المتجر داخل الإدخال، فلا يستطيع مالك قديم الكتابة أو تغيير موعد الجولة الجديدة. لا يستبدل fencing القفل الاستشاري، بل يعالج فقد اتصاله المنفصل. [أقفال PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html)، و[مهل معاملات Prisma](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

SyncRun واحد بنطاق SYNCHRONIZATION لكل جولة جلب، دون سجلات BATCH إضافية لكل صفحة. يعيد استخدام `OfferIngestionService.ingest` ويحدث العداد داخل معاملة الصفحة. الحالات: SUCCEEDED أو PARTIAL أو FAILED أو CANCELLED، مع عدد الصفحات والمحاولات والسجلات المتخطاة والمدة وكود آمن. الأخطاء الخام وروابط تحوي مفاتيح لا تسجل. السجلات القديمة الخاصة بالإدخال اليدوي تبقى BATCH.

النجاح الجزئي يحافظ على الصفحات المحفوظة ولا يحذف القديم. `partial` أو skippedCount من المزود ينهي الجولة كتغطية غير كاملة. تعطل مصدر لا يوقف محاولة مصادر أخرى. لا تنشر البيانات الاصطناعية بإزالة وسمها؛ يُعاد التحقق من نوع المصدر ووسم البيانات قبل الإدخال حتى إذا تغير السجل أثناء الجلب.

## البيانات القديمة والاحتفاظ

`staleAt = fetchedAt + staleAfterSeconds`. مرور العتبة يجعل العرض قديمًا، دون ادعاء أنه نفد من المخزون. يستبعد من Deals ويظهر `isStale=true` في معلومات منتجات ما زالت محتوياتها ضمن الترخيص. `expiresAt` حد الاحتفاظ المنفصل؛ المصدر القديم أو الغائب لا يحصل على تمديد عمر دون جلب ناجح.

حلقة التنظيف منفصلة عن حلقة المزامنة داخل العامل، وتستخدم قفلًا عامًا لمنع منظفين متزامنين. تعيد استخدام purgeExpired من المرحلة الثالثة: تحذف المنتهي وتمحو النص والصورة المنتهيين وتزيل المنتج اليتيم المنتهي فقط. لا تحذف عرض متجر صالحًا مرتبطًا بمنتج انتهى محتواه؛ يظل الرابط محفوظًا لكن المنتج قد يكون مخفيًا حتى تحديث محتواه من مصدر مصرح.

التنظيف يحتاج عاملًا يعمل واتصال DB متاحًا؛ لا يمثل مؤقت البرنامج ضمان حذف فوري عند انقطاعه. يبقى `db:purge-expired` إجراء إداريًا مستقلًا. عند إضافة مصدر تجاري لاحقًا يجب اختيار فترة تنظيف أصغر من مهلة الترخيص بهامش كافٍ ومراجعة حالة الانقطاعات قبل التشغيل. لا يوجد price_history أو أرشفة استجابات خام.

## خوارزمية Deal Score

المحرك المستقل في `src/scoring/deal-scoring.ts` يستخدم Decimal للحساب، وPostgreSQL numeric لترتيب النتائج قبل Pagination. يقارن اختبار تكامل النتيجتين. لا نخزن رقم Score قديمًا في الجدول؛ يُحسب عند القراءة بالوقت نفسه للاستعلام وتفسير النتيجة، فتنخفض مساهمة الحداثة دون انتظار تشغيل Worker.

إذا غاب السعر/العملة الصالحان، أو انتهت البيانات، أو أصبحت قديمة، أو كانت UNAVAILABLE، فالدرجة صفر. وإلا:

| المكون | الحد الأقصى | القاعدة الافتراضية |
| --- | --- | --- |
| الخصم | 35 | `min(verifiedDiscount, 50) / 50 * 35`؛ لا شيء دون referencePriceTrusted ومرجع موجب أعلى من الحالي |
| الحداثة | 25 | `max(0, 1-age/stalenessWindow) * 25` |
| التوفر | 20 | AVAILABLE فقط؛ UNKNOWN لا يكسب هذه النقاط |
| اكتمال البيانات | 10 | نصف المكون لرابط المنتج ونصفه للصورة عند وجودهما |
| الشحن | 10 | إذا كان معلومًا بنفس العملة: `clamp(1-shipping/current,0,1)*10`؛ المجهول صفر نقاط ولا يُعد مجانيًا |

للمنتج ذي السعر صفر، يكتسب مكون الشحن فقط إن كان الشحن صفرًا معلومًا؛ لا يقسم على صفر. تُجمع المكونات وتقرب الدرجة إلى منزلتين من 100. TOP_DEAL يتطلب أيضًا سعرًا مرجعيًا موثوقًا أعلى، وAVAILABLE، ودرجة لا تقل عن 65. خصم كبير وحده لا يكفي، وUNKNOWN قد يبقى منتجًا مخفضًا دون أن يتأهل لاختيار Top.

`IngestionItem.referencePriceTrusted` ثقة يجب إثباتها من المصدر ومراجعته، وليست استنتاجًا من فرق السعرين. القيم الاصطناعية المضبوطة تعامل كمراجع اختبار موثوقة افتراضيًا للمحافظة على Fixtures السابقة؛ ليست دليل تاريخ سعر تجاري. بيانات تجارية قديمة لم تُكتسب الثقة تلقائيًا في Migration. يظل المرجع غير الموثوق موسومًا ولا يمنح نسبة خصم أو نقاط خصم. `shippingCost` اختياري ضمن سياق الإدخال وبعملة العرض، ولا يُخترع من غياب حقل الشحن.

قواعد قابلة للتعديل من Environment Variable JSON، مع بقاء مجموع الأوزان 100:

```dotenv
DEAL_SCORING_RULES={"discountWeight":35,"freshnessWeight":25,"availabilityWeight":20,"qualityWeight":10,"shippingWeight":10,"discountCap":50,"topThreshold":65}
```

تقرأ عند بدء Express ويجب إعادة تشغيله لتغييرها. ترفض القواعد غير الصالحة بدل استخدام أوزان غير متوقعة. لا توجد عتبة «سعر منخفض» موحدة بين العملات أو التصنيفات؛ يحددها الطلب صراحة. لا يوجد AI أو ML، والدرجة تقدير قابل للتفسير لا ضمان لجودة المنتج أو صحة الادعاءات التجارية.

## REST API

```text
GET /api/v1/deals?view=top&sort=score_desc
GET /api/v1/deals?sort=newest
GET /api/v1/deals?sort=discount_desc
GET /api/v1/deals?view=low_price&currency=USD&maxPrice=20
GET /api/v1/deals?view=discounted&merchantId=<uuid>&market=US&currency=USD
GET /api/v1/products?sort=score_desc
```

المتجر والتصنيف والسوق والعملة وq ونطاق السعر وPagination تظل مدعومة. `view` خاص بـDeals، والافتراضي discounted؛ اختيار top يرتب بالدرجة افتراضيًا ما لم يطلب ترتيبًا آخر. low_price يحتاج العملة وmaxPrice، ويمكن أن يشمل منتجات بلا تخفيض. `selection` في الاستجابة يبين الاختيار، و`scoreClassification` يبين PRODUCT أو DISCOUNTED_PRODUCT أو TOP_DEAL أو INELIGIBLE مستقلًا عن سقف السعر الذي حدده العميل.

كل عرض يحتوي dealScore وscoreComponents وscoreReasons وreferencePriceTrusted وshippingCost وisStale. ترتيب Score والعد قبل Pagination في PostgreSQL، وليس فرز صفحة مقتطعة في الذاكرة. النسب والأسعار والدرجة نصوص. لا تحويل عملة ولا مقارنة أسعار مختلفة العملات.

أمثلة التحقق الفعلي من العامل المبني إلى PostgreSQL إلى Express المبني: [SYNC_EXAMPLE.json](SYNC_EXAMPLE.json). تتضمن خمس سجلات قبل وبعد إعادة تشغيل Upsert، ونتيجة جولة من ثلاث صفحات وأربع قراءات HTTP. كلها اصطناعية.
